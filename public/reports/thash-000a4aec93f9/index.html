A Compilation-Based Under-Constrained Execution Engine

总结

软件漏洞（特别是Linux内核等大规模软件系统中的漏洞）对系统安全性和正确性构成了重大挑战，而现有的静态分析误报率高，动态测试则受限于测试用例编写和环境搭建的复杂性。

As-is: 现有的欠约束执行引擎（如UC-KLEE、Angr）虽然能够通过延迟初始化技术解决从任意函数开始执行时的内存初始化问题，但它们均基于解释器实现，导致性能极其低下。具体而言，KLEE比原生执行慢约3000倍，Angr更是慢超过321,000倍。这种严重的可扩展性问题使得它们难以应用于文件系统、TCP协议栈或设备驱动等稍大型的组件分析。

To-be: 本文提出了UCSan，一个基于编译的欠约束执行引擎。UCSan通过LLVM Pass和运行时库将任意C/C++函数集编译为自包含的可执行文件，无需手动修改代码。它引入了Just-In-Time Initialization (JITI) 技术来处理内存初始化和指针翻译，并利用Shadow Pointers跟踪指针别名。评估结果显示，结合SymSan后的UCSan†在Linux内核分析任务上比基于KLEE的引擎快15.06倍，能够成功编译超过80%的Linux内核模块（版本4.14, 5.10, 6.16）。在静态分析警告过滤任务中，UCSan†在2分钟内处理了63,957个警告（比KLEE多处理42,155个），并确认了至少15个额外的已修补漏洞，显著提升了漏洞检测的有效性和应用范围。

背景

软件漏洞是计算机系统正确性和安全性的主要威胁，尤其是对于作为整个系统可信计算基（TCB）的操作系统内核而言。一旦内核漏洞被利用，通常会导致整个系统被攻破。

目前主流的漏洞发现技术包括动态测试（如灰盒模糊测试）和静态分析。动态测试（如OSS-Fuzz和syzbot）虽然发现了大量漏洞，但存在两个根本性挑战：一是需要良好的测试工具，如果漏洞无法从测试工具触达，就无法被发现；二是环境搭建困难，例如测试内核需要虚拟机，测试文件系统需要磁盘镜像，测试驱动需要硬件或模拟器。并非所有组件都能被有效测试。

静态分析虽然不受测试工具限制且能覆盖整个代码库（如整个内核），但需要在可扩展性上牺牲精度。对于大型复杂项目，静态分析器往往产生过多的误报。例如，论文中使用的use-before-initialization分析器生成了147,643个警告，但仅有52个被确认或修补。

理想的方法是提取目标软件的任意代码子集，使其自包含，然后对其应用动态测试技术。这既避免了复杂的测试工具和环境搭建，又能利用动态分析的精度。然而，这面临两个关键挑战：如何正确初始化内存（特别是堆对象）以及如何处理外部依赖。虽然UC-KLEE等欠约束执行引擎通过延迟初始化提供了一种自动化解决方案，但它们基于解释器的实现导致了严重的性能瓶颈，无法满足大型组件分析的需求。

问题

本文旨在解决基于解释器的欠约束执行引擎在可扩展性方面的根本性缺陷，具体包括以下几个技术难题：

1. 性能瓶颈：现有的解释器引擎（如KLEE、Angr）执行速度极慢（比原生代码慢数千甚至数十万倍），无法扩展到分析文件系统、TCP栈或设备驱动等大型软件组件。

2. 内存初始化：当从任意内部函数开始执行时，跳过了常规的初始化过程（如内核启动），堆内存对象未被分配和初始化。如果直接执行，程序会因无效内存访问而崩溃。需要一种按需分配和初始化内存对象的机制。

3. 指针处理：在欠约束执行中，指针可能是未初始化的。需要处理指针别名（C1）、估计内存对象大小（C2）、动态调整对象大小（C3，例如由于`container_of`操作）以及从输入文件反序列化内存对象以确保确定性执行（C4）。

4. 外部依赖：提取的代码可能会调用分析范围之外的函数。需要一种机制来自动处理这些外部函数调用，例如提供简化模型、替换函数（如将`kmalloc`替换为`malloc`）或假设其为纯函数。

解决方案

本文提出了UCSan（Under-Constrained Sanitizer），一个基于编译的欠约束执行引擎，旨在解决上述问题。UCSan作为LLVM Pass和运行时库实现，主要由编译时插桩和运行时支持两部分组成。

1. 系统架构与工作流

UCSan接受LLVM IR和YAML配置文件作为输入。配置文件指定了分析范围（包含哪些函数）、入口函数（从哪里开始执行）以及外部函数的处理策略。UCSan通过`opt`工具进行插桩，移除范围外的代码，并根据配置处理外部函数调用。最终，它将插桩后的IR编译并链接必要的运行时库，生成一个独立的用户空间可执行文件。

2. 编译时插桩

UCSan在编译时对代码进行转换，主要包括以下三个方面：

* 测试工具生成：UCSan自动插入一个`main`函数，负责创建影子指针、从输入反序列化参数（如果有），并调用目标入口函数。

* 指针翻译：UCSan将程序中的指针分为“伪指针”和“实指针”。伪指针由PUT管理，包含逻辑偏移量，不能直接解引用；实指针是有效的虚拟地址。UCSan在所有涉及指针操作的LLVM指令（如Load, Store, GEP, BitCast）前插入`check_ptr`调用。关键不变量是：实指针绝不能逃逸到PUT的数据流中，仅用于内存访问指令，随后立即丢弃。

* 影子指针：为了支持指针翻译，UCSan利用LLVM的DataFlowSanitizer (DFSan)框架的影子内存设计。影子指针与伪指针一起传播，记录逻辑基址、指向的对象以及来源。这解决了指针别名问题。

* 外部函数处理：UCSan提供三种策略处理外部函数：自定义包装器（Custom Wrapper，如映射`kmalloc`到`malloc`）、假设纯函数、假设任意更改（保守地重新分配所有指针参数）。

3. Just-In-Time Initialization (JITI)

JITI是UCSan的核心运行时机制，用于解决内存初始化挑战。它将指针翻译过程概念化为类似x86处理器的分段机制，其中影子指针充当段寄存器。

* 伪指针：存储内存对象内的逻辑偏移量，并满足具体执行中的路径约束（如`p != NULL`）。

* `check_ptr`运行时逻辑：

1. 指针验证：检查输入指针是否为伪指针。

2. 延迟分配：如果伪指针指向的对象尚未分配，UCSan根据指针类型（如指针运算、类型转换）推断大小并分配新内存对象。如果推断大小不足（如`container_of`），会自动重新分配。

3. 初始化：检查测试输入是否为该对象提供了具体值。如果有，则填充内存；否则初始化为零。同时初始化影子内存以跟踪数据来源。

4. 指针翻译：将伪指针转换为实指针。计算公式为：`object_base + (current_offset - base_offset)`。

4. 输入与种子组成

为了支持路径探索，UCSan定义了一种结构化的种子格式来序列化内存对象。

* 超级对象：ID为0，作为所有“根”欠约束值的容器，包括入口函数的初始参数、全局变量和外部函数的返回值。

* 链式对象：对于通过指针访问的对象（如链表节点），使用解引用链进行标识。每个对象记录其基指针的来源（`<source_obj_id, offset>`），通过反向追溯来源可以唯一标识对象。

5. 内存安全检查器

UCSan复用了影子内存基础设施，实现了类似AddressSanitizer (ASan)的检查功能，包括越界访问（OOB）、释放后使用（UAF）和未初始化使用（UBI）检查，且无需额外的Sanitizer Pass。

测试结果

论文通过一系列实验评估了UCSan的性能、兼容性和漏洞发现能力。

1. 性能与兼容性

* 基准测试：在nbench基准测试中，UCSan与KLEE和Angr进行了对比。结果显示UCSan比这些解释器引擎快数个数量级。

* 内核兼容性：UCSan成功编译了Linux内核版本4.14、5.10和6.16。在不同配置下，它能够成功编译超过80%的内核模块。

2. 漏洞发现能力

为了展示UCSan在漏洞发现方面的优势，作者开发了Thoroupy（一个Python分析伴侣）与UCSan结合，形成了一个完整的混合执行引擎UCSan†。

* 静态分析警告过滤：在UBITect生成的静态分析警告过滤任务中，UCSan†在2分钟的超时时间内处理了63,957个警告（占总数的95.46%），而基于KLEE的引擎仅处理了21,802个。UCSan†多处理的42,155个警告使其能够确认至少15个额外的已修补漏洞。

* 漏洞复现：UCSan†应用于复现已知的用户空间开源项目和Linux内核中的100多个漏洞。结果显示，UCSan†能够成功复现其中的很大一部分，且无需任何手动构建测试工具的工作。

3. 局限性

* 内联汇编：当前原型使用启发式方法处理常见的内联汇编模式，复杂的汇编块需要使用自定义包装函数手动建模。虽然LLM可以辅助生成包装器，但这仍是一个潜在的手工负担。

* 类型安全：内置的检查器在分配级别运行，不执行类型安全检查，因此无法检测结构体内部的越界访问（例如溢出到同一结构体内的相邻字段）。
