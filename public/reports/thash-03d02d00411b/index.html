No Buffer, No Bottleneck: Efficient Zero-Copy KV Cache Offloading for Long-Context LLMs

总结

长上下文大语言模型（LLM）在推理过程中需要维护线性增长的 KV 缓存，数百 GB 的缓存需求远超 GPU HBM 容量，而现有卸载方案依赖 GPU 暂存缓冲区，造成显存浪费和 CPU–GPU 传输量翻倍。本文针对 NVIDIA GH200/GB200 等 NVLink-C2C 异构平台，提出了首个零拷贝 KV 缓存卸载系统 DirectKV，通过内核–内存协同设计消除暂存缓冲区并大幅缓解数据搬运瓶颈。

As-is: 现有 KV 缓存卸载系统（如 Pie、FlexGen、Neo 等）采用 swap-based 模型，将 KV 块存储在 CPU 内存中，但在注意力计算前必须通过显式的 `cudaMemcpyAsync` 将 KV 块搬运到 GPU 暂存缓冲区中。这一设计存在三大痛点：（1）暂存缓冲区占用宝贵的 GPU HBM 显存；（2）逐层 swap-in/swap-out 导致 CPU–GPU 传输量翻倍；（3）动态传输地址破坏 CUDA Graph 的可重放性。即便在 NVLink-C2C（900 GB/s）平台上，现有系统仍无法充分利用带宽，因为注意力内核假设所有操作数均驻留于 HBM。而朴素零拷贝方案虽然省去了缓冲区，但由于矩阵乘法中重复从 CPU 内存取数，在 PCIe 上慢 20 倍、在 NVLink-C2C 上仍慢 2 倍，且 L2 缓存命中率从 ~77% 骤降至 32.3%。

To-be: DirectKV 通过三项核心技术使零拷贝在实践中可行：（1）CPU 内存感知的 tiling 策略，将带宽压力从 CPU–GPU 互连转移到高带宽 HBM，将 CPU 到 GPU 的数据流量从 33.5 GB 降至 0.4 GB；（2）warp 级流水线，重叠数据搬运与计算，HBM 吞吐提升 4.3 倍；（3）内核融合，将 KV 投影与注意力计算合并为单个 CUDA 内核，消除冗余 KV 往返传输，延迟降低 49%。在 GH200 上，DirectKV 相比现有方案 CPU–GPU 传输量最多减少 50%，GPU 显存占用降低 43%，端到端性能提升最高 1.2 倍，同时保持完整的注意力精度。

背景

长上下文 LLM 与 KV 缓存

长上下文 LLM 支撑多轮对话、上下文学习和长程代码生成等应用。在自回归推理中，每个新 token 的 query 需要 attend 到所有历史 token 的 K/V 张量。KV 缓存将注意力计算复杂度从序列长度的平方降为线性，但代价是缓存大小随序列长度和模型维度线性增长。对于 128K token 的十亿参数级 LLM，仅 KV 缓存就可能需要数百 GB，远超 GPU HBM 容量（如 GH200 的 96 GB HBM3）。

KV 缓存卸载的演进

现有系统探索了多种 CPU 卸载策略：

- Swap-based 方案（如 Pie、FlexGen）：将 KV 块放在 CPU 内存或 SSD 中，使用 GPU 暂存缓冲区通过 GPU copy engine 进行搬运，尝试与计算重叠。但 PCIe 带宽（64 GB/s）远低于 HBM 带宽（4 TB/s），且逐层 swap-in/swap-out 使互连流量翻倍。此外，显式的 `cudaMemcpyAsync` 操作地址随解码步动态变化，破坏 CUDA Graph 的可重放性。

- 远程/分解内存方案：将 KV 存储在远程内存中按需拉取，但仍遵循 swap-like 模型，KV 必须先暂存到 GPU 内存。

- 部分/完全 CPU 卸载方案（如 Neo）：将部分或全部注意力计算移至 CPU，牺牲 GPU 的完整计算能力。

NVLink-C2C 带来的新机遇

NVIDIA GH200/GB200 超级芯片通过 NVLink-C2C 提供高达 900 GB/s 的双向带宽，是 PCIe Gen5 的 7 倍。这使 CPU 内存有望成为 GPU KV 缓存容量的实用扩展。然而，现有系统（如 Pie）仍依赖 HBM 暂存缓冲区，无法充分利用这一能力。

零拷贝的挑战与机遇

零拷贝允许 GPU 内核直接访问 CPU 驻留的 KV 张量，消除暂存缓冲区。但朴素零拷贝性能极差：矩阵乘法内核为 HBM 驻留张量调优，反复从 CPU 内存取数暴露带宽差距并降低 L2 缓存命中率。论文的关键观察是：共享内存（SMEM）可作为快速片上缓冲区，通过灵活的 tiling 策略重构矩阵乘法的数据访问模式，将带宽压力从 CPU–GPU 互连转移到 HBM，使零拷贝在不依赖暂存缓冲区的情况下接近 HBM 驻留性能。

---

问题

论文聚焦的核心问题可以精确表述为：如何在不使用 GPU 暂存缓冲区的前提下，实现高效的零拷贝 KV 缓存卸载，同时充分利用 GPU 计算能力进行高性能注意力计算？

具体而言，朴素零拷贝面临三重挑战：

1. 带宽放大效应：在矩阵乘法 C = A × B 的 O(n³) 计算中，若 B 驻留在 CPU 内存，每个 (i, j, k) 三元组都需要重新加载 B 的 tile。论文的测量显示，原始 tile 大小仅 10.6 GB，但零拷贝导致 CPU 到 GPU 的实际流量膨胀至 33.5 GB——超过 3 倍放大。在 NVLink-C2C 上，这导致 106 ms 延迟（相比 HBM 驻留的 52 ms，慢 2 倍）。

2. L2 缓存效率崩塌：由于 CPU–GPU 传输（单向 450 GB/s）远慢于 HBM 到 L2 传输（4 TB/s），零拷贝导致频繁停顿。Baseline 和 Swap 的 L2 命中率约 77%，而零拷贝降至 32.3%——下降 58%。CPU 到 GPU 流量从 21.1 GB 增至 22.7 GB。

3. 内核分离导致的冗余传输：传统实现将 KV 投影和注意力计算作为独立 CUDA 内核启动。投影内核生成的 K/V 必须写回 CPU 内存（更新 KV 缓存），再由注意力内核重新读取——造成冗余的 CPU–GPU 往返传输，加剧带宽瓶颈。

此外，swap-based 方案还存在 CUDA Graph 兼容性问题：动态 KV 块选择导致 `cudaMemcpyAsync` 地址变化，迫使图更新或重新捕获，削弱了 CUDA Graph 在实际服务系统中的收益。

解决方案

DirectKV 的系统架构（见图 8）包含四个核心组件：Kernel Generator（离线内核生成）、Kernel Adaptor（运行时内核选择）、Attention Fusion Engine（投影-注意力融合）和 KV Cache Manager（零拷贝缓存管理）。以下详细阐述其关键技术。

1. CPU 内存感知的 Tiling 策略

这是 DirectKV 的核心创新。传统 tiling（NativeTiling）迭代 A 和 B 的 tile，C 保持驻留在寄存器/SMEM 中。当 B 驻留在 CPU 内存时，B 的流量随 O(n³) 计算放大。

DirectKV 的 CPU-aware tiling（CpuAwareTiling）反转了这一模式：将 B tile 设为驻留（stationary），改为迭代 A 和 C 的 tile。具体而言：

- 每个 B tile 从 CPU 内存经零拷贝加载到 SMEM 后，仅获取一次（每个 (k, j) 对），被所有 i 复用，将 CPU 到 GPU 流量从 O(n³) 降为 O(n²)。

- 代价是 C 需要从 HBM 反复加载和写回（从 NativeTiling 的 2·O(n³) 增至 3·O(n³)），但 HBM 带宽（4 TB/s）比 CPU–GPU 互连（900 GB/s）高约一个数量级，额外开销可被有效吸收。

在矩阵乘法基准测试中（n=10240，每个矩阵 400 MB），该策略将 CPU 到 GPU 流量从 33.5 GB 降至 0.4 GB，HBM 流量增至 61.8 GB + 33.9 GB，延迟从 106 ms 降至 54 ms（提升 49%），L2 命中率从 32.3% 回升至 75.1%。

2. Warp 级流水线

利用 Hopper 架构的多 warp group 并发能力，DirectKV 将线程块内的 warp 分为不同组，分别负责数据搬运和计算：

- Producer warps：从 HBM 或 CPU 内存预取下一个 tile 到 SMEM。

- Consumer warps：在当前 tile 上执行计算。

- Storer warps（仅 prefill 阶段）：将中间结果（如 K/V）写回 CPU 内存。

这种重叠有效隐藏了内存延迟。基准测试显示，warp 级流水线在数据量几乎不变的情况下，将 HBM 吞吐从 0.3 TB/s 提升至 1.3 TB/s（4.3 倍），延迟降低 11%（从 54 ms 到 48 ms）。Hopper 架构的 Tensor Memory Accelerator（TMA）进一步支持异步数据搬运，释放计算 warp 专注于算术运算。

3. 内核融合：投影 + 注意力

传统分离内核设计中，投影内核生成 K/V 后写回 CPU 内存，注意力内核再重新读取——造成冗余往返。DirectKV 将 KV 投影和注意力计算融合为单个 CUDA 内核（见图 9）：

- Prefill 阶段（Algorithm 2）：使用三个 warp group（producer、consumer、storer）。投影阶段分两步生成 K 和 V tile，生成的 K/V tile 保留在 SMEM 中，立即被后续注意力计算消费，同时 storer warps 异步将 K/V 写回 CPU 内存更新缓存。注意力阶段迭代 Q（驻留 HBM），对每个 (K,V) tile 计算注意力分数，使用 streaming softmax 保证数值稳定性。可选地应用 RoPE（每个 K tile 独立变换，无 inter-tile 依赖）。为避免 O_i 的写-读依赖，不同 SM 分配不同的 head-batch 对。

- Decode 阶段（Algorithm 3）：仅需两个 warp group（producer、consumer），因为只需写回单个新 token 的 K/V。策略与 prefill 互补——迭代所有缓存的 (K,V) tile（从 CPU 内存零拷贝加载），对单个 query q_t 计算注意力。输出 o_t 保留在寄存器中跨迭代复用，避免反复从 HBM 读取。新 token 的 K/V 投影完成后追加到 CPU 内存中的 KV 缓存。

内核融合在基准测试中将延迟从 85 ms 降至 57 ms（49% 加速），HBM 吞吐从 0.3 TB/s 提升至 1.9 TB/s。

4. SMEM 分区与复用

SMEM 容量有限（GH200 上 256 KB 的统一 L1/SMEM 池），DirectKV 将其逻辑分为投影缓冲区（存储 X、W_k、W_v tile）和注意力缓冲区（存储 K、V、Q、O）。为缓解压力，K 复用 W_k 的缓冲区，V 复用 W_v 的缓冲区。默认采用 2 级流水线（缓冲需求翻倍），保守保留 80% 的统一池给 SMEM。SMEM 分配需满足约束：α·P ≥ 3·m·size(T)·(Dim·N)，其中 P 为池大小，α=0.8，m=2（流水线级数），T 为数据类型，Dim 为 KV 头维度，N 为 tile 大小。

5. 离线内核生成与运行时适配

Kernel Generator 使用 C++ 模板在离线阶段为不同配置 `<T, Dim, N>`（如 FP16/128/64、BF16/64/64 等）预编译融合内核，确保编译器完全优化且无运行时代码生成开销。Kernel Adaptor 在运行时根据张量精度、头维度和执行阶段（prefill vs. decode）从候选池中选择最匹配的内核，实现轻量级动态适配。

6. KV Cache Manager

使用 `cudaHostAlloc` 分配 pinned memory 作为 KV 缓存缓冲区，使主机内存页锁定且 GPU 可直接访问。KV 张量一旦生成即驻留在 pinned buffer 中，跨解码迭代复用，无需重新计算或冗余传输。Prefill 阶段存储初始 K/V，decode 阶段 GPU 直接复用缓存条目并追加新 token 的 K/V。

测试结果

实验设置

- 硬件：NVIDIA GH200 Grace-Hopper Superchip（Hopper GPU、96 GB HBM3、LPDDR5X CPU 内存、NVLink-C2C 900 GB/s）。基线对比使用 H100（PCIe Gen5）以量化 NVLink-C2C 的优势，两者 GPU 架构相同。

- 软件：CUDA 12.4、PyTorch 2.3、CUTLASS 3.0+（含 Hopper 支持的 CuTe）。DirectKV 原型基于 FlashAttention-3 扩展，约 5,300 行 CUDA/C++ 代码。

- 模型：Llama-3.1-8B、OPT-13B、OPT-30B。

- 数据集：ShareGPT（用户共享 ChatGPT 对话）和 Alpaca（GPT-3.5 生成的指令跟随数据），请求到达按泊松过程生成。

- 工作负载：请求率最高 30 req/s，上下文长度 1K–32K token；额外压力测试使用更高请求率和更长上下文。

- 基线系统：

- SGLang：HBM 驻留基线，KV 缓存全存 GPU 内存。

- Pie：使用大 GPU 暂存缓冲区，通过 NVLink-C2C swap KV 块。

- FlexGen：使用 GPU/CPU/磁盘 + 4-bit 压缩 + 成本模型搜索。

- Neo：将部分注意力计算和 KV 缓存卸载到 CPU。

端到端性能

Per-token 延迟（图 10）：在三种模型上评估不同请求率下的 per-token 延迟。

- Llama-3.1-8B：SGLang 在所有请求率下延迟最低（KV 缓存可完全放入 HBM）。DirectKV 略慢于 SGLang 但大幅优于其他卸载系统——在 30 req/s 下，DirectKV 为 0.75s，而 Neo/Pie/FlexGen 为 1.55–2.95s。

- OPT-13B：SGLang 在最高请求率下 OOM。DirectKV 在 30 req/s 下仍可运行，延迟 0.75s，而其他卸载系统为 1.55–3.95s。

- OPT-30B：SGLang 仅支持低请求率。DirectKV 可扩展至 30 req/s，且在高负载下延迟远低于 Neo、Pie 和 FlexGen。

上下文长度影响（图 11）：DirectKV 在所有支持的上下文长度上始终实现最低延迟，平均加速 1.2 倍。随着序列长度增长，DirectKV 的优势增大——在 16K token 时，DirectKV 的领先更为显著（论文文本在此处截断，但趋势明确）。在内存使用方面，SGLang 在较长序列下 OOM，而 DirectKV 通过零拷贝卸载避免了 GPU 显存耗尽。

局限性

根据论文内容可识别以下局限：

1. 硬件依赖：DirectKV 专为 NVIDIA GH200/GB200 等 NVLink-C2C 平台设计，在 PCIe 平台上朴素零拷贝仍慢 20 倍，系统优势高度依赖高带宽互连。

2. SGLang 差距：当 KV 缓存可完全放入 HBM 时，SGLang 仍优于 DirectKV，因为零拷贝无法完全消除 CPU–GPU 带宽差距（900 GB/s vs. 4 TB/s）。

3. HBM 流量增加：CPU-aware tiling 将带宽压力转移到 HBM，HBM 流量约增加 2 倍（从 33.5 GB 增至 61.8 GB + 33.9 GB），在 HBM 带宽已被其他操作占满的场景下可能成为新瓶颈。

4. SMEM 容量约束：SMEM 分区策略和流水线级数受限于统一 L1/SMEM 池大小（GH200 上 256 KB），可能限制更大 tile 或更多流水线级的使用。

5. 论文文本截断：完整的上下文长度实验结果和部分消融分析在提供的文本中不完整，无法获取全部实验细节。
